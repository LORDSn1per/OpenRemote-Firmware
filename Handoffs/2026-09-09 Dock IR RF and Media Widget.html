01RF433: four bugs in a stack

Each one hid the next, and every log line along the way reported success.

This is the important shape of the whole job. A learned RF code could not be sent, and fixing the first cause simply revealed the second. Nothing failed loudly — the firmware consistently reported that it had transmitted.

  1. The payload encoding was thrown away 4.26

    ESP-NOW is a routing overlay: a code is decoded to RAW timings, then kind is overwritten with ESPNOW so it routes to the dock. That overwrite destroyed the only record of which decode had happened, and buildEspNowPayload() tests kind against RAW and PARSED — so it matched neither and refused every ESP-NOW command ever sent.

    The command now carries espNowEncoding, recorded before kind is overwritten.

  2. It was not routed as RF at all 4.27

    The dock's MAC was resolved to a list index at parse time. Re-pair a dock after the config was parsed and the lookup failed, leaving the command as ordinary IR — which then went through relayIrToDock(), and that function forces the transport to IR.

    The MAC now travels on the command and is resolved at send time, so re-pairing needs no re-sync.

  3. The dock was on another channel 4.28, 4.34–4.36

    espNowChannel is adopted from the remote's own station, which is only correct while both are on the same access point. A mesh had roamed the remote to channel 1 while the dock sat on 8. Worse, the keepalive ping states the remote's instantaneous channel and the dock believes it — so while the station associated and hopped 1 → 6 → 8, the dock chased each value, writing flash every time.

    The remote now states a channel only when settled, and the dock applies a move immediately but waits six seconds before saving.

  4. The capture itself was corrupt dock 1.42, 1.43

    Once the code finally reached the air, the fan still ignored it. Printing the payload showed why.

    The 60000 was a 60 ms gap clamped and stored as an edge. And RF_END_GAP_US was 20 ms while that remote repeats every 5.2 ms, so the capture ran through repeat after repeat, filled the 300-edge buffer and was truncated to 120 to fit one frame — cutting the code in half. Then, once fixed, the trailing silence was being discarded, and that gap is the sync the receiver frames on.

Also required: the frame budget

Two different header sizes shared one 250-byte ESP-NOW frame. The learn reply's header is 7 bytes, so it could return (250−7)/2 = 121 timings; the command frame's header was 35 bytes, so it could carry only (250−35)/2 = 107. Anything landing in that 108–121 band — where an ordinary 433 MHz burst falls — was learned, stored and displayed perfectly, then refused at send time. The 25 PARSED-only bytes moved to the end of the header and are not sent for RAW frames, lifting the ceiling to 120, with the dock's RF_SEND_MAX pinned to the same number.

02Dock IR: the timing was 30% long

The emitter was fine. Every log line was fine. The edges were not.

The orange test LED blinked, the IR LED showed the usual faint purple on a phone camera, and the codes were correct — yet a heater that obeyed the same command from the remote ignored every one from the dock. A probe pattern of round numbers made it measurable.

Carrier methodOverhead per edgeEffect on a 600 µs mark
IRremote, software carrier88 µs15% long
IRremote, LEDC hardware carrier178 µs30% long
RMT peripheral7 µs1% long

IRremote drives the pin from the CPU with a library call per edge, and a single-core C3 also running Wi-Fi, MQTT, a WebSocket and ESP-NOW cannot keep up. Note the middle row: moving the carrier into LEDC hardware made it worse, because ledcWrite costs more per call than the bit-banging it replaced. RMT generates carrier and envelope in hardware from a symbol list, so the CPU hands over the whole burst.

Then the carrier was on the wrong half

RMT timing was exact and the heater still ignored it — while jamming the real remote beside it. That was the clue: real energy, meaningless content.

Passing true put the 38 kHz on the spaces instead of the marks. And the duty argument is a fraction 0–1, so 33.0f tripped the core's own range check and was silently replaced with 0.5. Correct values: false and 0.33f.

Parsed protocols needed the same treatment

Only raw codes went through RMT at first. A Flipper .ir file is mostly parsed entries, and those still used IRremote's encoders — a 9000 µs header arrived broken into three fragments, because the software carrier stops whenever the CPU is preempted and the receiver reads every dropout as the end of a mark. Nine protocols are now rendered to timings on the dock: NEC, NECext, Samsung32, SIRC/15/20, RC5, RC5X, RC6. Constants were transcribed from the IRremote source the remote transmits with — the goal was not "a correct NEC frame" but the same frame the remote sends, since the whole database already works from there. Kaseikyo, NEC42, Pioneer and RCA were added afterwards in shared/openremote_ir_extra_protocols.h, compiled into both firmwares from one file.

03Media widget: Cast V2 on the dock

It had never been connected to anything.

nowPlaying was written exactly once — by its own initialiser, with valid = false — and all fourteen other references were reads. "Nothing playing" was the only state the widget could reach. Bluetooth was a red herring: the BLE link is HID, one-way, and carries no metadata.

The protocol was prototyped in Python against five real Chromecasts before any firmware was written, and that changed the design twice. The most useful finding is counter-intuitive: what is available depends on the app, not the device type. Both an oval Chromecast and a Google TV Streamer report a session for apps running natively on them.

So SmartTube gives title, subtitle, artist and duration; the Apple TV app gives only play state and position. The widget shows the app name when there is no title, which is the honest fallback. The dock hosts the client because it is mains powered — polling from the remote would wake its radio every few seconds, the opposite of the point. It watches one Chromecast, named by the remote, and WebConfig has a Scan button that lists what the dock can see.

04What worked — repeat this

DOCapture both boards on one clock, then read

Every real cause in this document came out of a dual serial capture, and several were invisible from either board alone. The RF fix took days of theorising and about ninety seconds once the remote's own serial was open during a WebConfig send.

DOPrototype the protocol on the Mac first

A Python Cast V2 client against five real devices settled the design before a line of firmware existed — and disproved a prediction I had already committed to in writing. Same for the IR database: the protocol distribution came from querying OpenRemote.irdb (169,910 parsed buttons), not from guessing what mattered.

DOBuild a round-trip test when correctness is not observable

The dock transmits one known frame per protocol; the remote's own IR receiver decodes what arrives. That checks timing constants, bit order, complement rules and carrier frequency at once, against hardware. It earned its keep immediately — RC5 and RC5X failed it, because they are the only protocols whose frame begins with a space and the accumulator was banking that leading space as the first entry. Inspection would never have caught it.

DODesign a probe that separates the two candidate causes

Every space arriving 150 µs long looked like the emitter stretching pulses. A symmetric probe — fifteen identical 2000 µs pulses — settled it: 29,980 µs received against 30,000 sent. A receiver can move the mark/space boundary but cannot change the period. The emitter was exact; the apparent error was receiver AGC, large at 600 µs and negligible at 2000.

DOVerify the version marker inside the built binary

strings firmware.bin | grep -x "4.43" before every flash and archive. Cheap, and it catches a silent no-op edit before it becomes a mislabelled release.

05What not to repeat

These are my wrong turns, in the order they cost time.

DON'TTrust a log line that says it succeeded

This was the theme of the entire job. Dock: IR sent in 147.19 ms while a fan code left the wrong emitter. pairing complete immediately before the host dropped. Every subsystem cheerfully reported success while doing nothing useful. When a symptom and a log disagree, the log is describing intent, not outcome.

DON'TRead component values off a zoomed-out schematic

I diagnosed a gate-drive failure from "R3 = 100 kΩ" and built a whole theory about the FET not slewing at 38 kHz. R3 is 100 Ω. The driver network was correct all along.

DON'TWiden a fix past the conditions you measured it under

4.35 extended the channel-recovery sweep to any unassociated station, reasoning nothing pinned the channel. Hardware disagreed: such a station is usually scanning, so it hops away from each channel the sweep sets. It tried all thirteen, reported "no dock answered on any channel" about a dock that answered seconds later, and burned most of a second per failed send. 4.36 reverted it.

DON'TRecommend Home Assistant for Android TV media titles

I suggested it, then checked properly: HA's Android TV Remote integration carries key events, power and current app — not media title. Only its ADB-based integration surfaces titles. Standing up a server would have landed exactly where Cast already was. The dock also cannot "be" Home Assistant — that is a Python application against 327 KB of RAM.

DON'TBlame the peer device before proving your own side

Bluetooth pairing stalled and I blamed the TV's stale pairing (already cleared), then my own Wi-Fi channel work (Wi-Fi and BLE share a radio — plausible, wrong). What actually settled it was a screenshot of the Mac's Bluetooth panel showing OpenRemote HID advertising healthily, then clicking Connect to force a real bond attempt.

The cause was rc=27 — BLE_HS_ESTORE_CAP, bond store full. The guard against it already existed and had never once run: the capacity check sat before applyBluetoothState(), but the store can only be read while the NimBLE host is up, so the count returned −1 and the bonds >= 0 guard skipped the block entirely.

DON'TCredit a fix to the last thing you changed

I attributed the heater finally working partly to fitting all four IR LEDs. Each LED works individually — power was never the limiting factor. The real fixes were the carrier polarity and RMT timing. The genuine hardware fault was different and simpler: R5 was unpopulated, and since the LED anodes are not commoned, D1 had no path to +5 V at all.

06Open items

  • Media widget on screen. The dock end is proven — it pulled SmartTube · My Dream Power Hammer Restoration! Part 6 · 1001/1413s off the Google TV. Needs a Media widget placed on a page, the Chromecast chosen via Scan, and one visual confirmation.
  • Artwork. Deferred deliberately: HTTP fetch, JPEG decode and SD caching on the remote, and the part most likely to hurt wake time. SmartTube published no images array anyway.
  • Forget pairing is one-sided. A BLE bond lives on both devices; the remote can only clear its own half. The other Chromecast keeps reconnecting until it also forgets. One line of text on that screen would prevent a recurrence.
  • Protocol sweep not re-run. The 27/27 result was on dock 1.52 / remote 4.28. Later changes don't touch that transmit path, but the sweep has not been repeated on 1.58 / 4.43.
  • Dock changelog gap. Entries for 1.34–1.39 were never written up, though the version string moved.
